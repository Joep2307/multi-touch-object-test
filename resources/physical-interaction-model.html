Physical Interaction Model

Twenty-five entities describing how loose contact points on a tabletop become a recognised object, how that object fires rules, and how those rules feed back into what the table shows.

The model splits into two kinds of thing, and that split colours every diagram below. Definitions are authored up front: a kind of object, a role, a rule, a state, a visual. Runtime exists only during a session: the block lying on the table right now, the role it was just given, the event from three seconds ago. Definitions can be versioned; runtime is gone when the session ends.

00

The loop that runs every second

Everything in this model serves a single circuit. The table sees contact points, not objects. A signature groups those points into something recognisable, that object gets a stable id, its movements become events, events test rules, and rules change state and image. Then a participant looks at the table and moves something again.

The hinge is PhysicalInstance: its id must not depend on the current number or position of contact points. If the table drops one point of a block, that is the same block in status Missing — not a new object.

01

From contact point to object

The table delivers only InputContact: a position, a size, a status. A PhysicalSignature states which combination of points forms one object — three points in a triangle with at most 5 mm deviation, rotation allowed, scaling not. A PhysicalKindDefinition bundles several signatures, so the same kind of object may be recognised in more than one way.

What comes out is the PhysicalInstance: the only object the rest of the system talks to. Its movement history lives in MotionHistory, its relation to neighbours in SpatialRelation, and every change becomes an InteractionEvent.

02

Rules and states

Behaviour is built from a single grammar of three words: when (TriggerDefinition), provided that (ConditionDefinition) and then (EffectDefinition). Two things use that grammar. An ActionDefinition is free-standing behaviour — cast a vote, place a marker, change the mode. A TransitionDefinition is the same pattern, but bound to a move between two states.

The duplication is deliberate: actions describe what a programme can do, states describe when it is allowed. A token in Voted simply no longer lists cast_vote in its enabledActionIds.

03

Session, modes and roles

The Session is the only place with real state: the active mode, the variables, the objects currently on the table, who holds which role, and the log. A ModeDefinition temporarily trims the rest — which actions exist, which roles take part, which table image applies. The same table with the same objects behaves differently in Voting than in Discussion.

With roles, the interesting detail is overflowPolicy: a physical table cannot stop a ninth block appearing when there are eight voters. So the model has to state explicitly what happens then, rather than designing the case away.

Why the log is append-only Every entry carries the mode it arose in. That makes five things possible with one structure: debugging, analytics, replaying a session, undoing an action, and accounting afterwards for how a vote came out.
04

What the table shows

The presentation layer describes image without behaviour. A PresentationDefinition knows which renderer it uses and what it binds to — position follows an object's pose, rotation follows its direction, colour follows the state, visibility follows the mode. It does not know why that state changed.

A RegionDefinition makes a piece of table meaningful: this is the voting area, and it accepts only these kinds of object and these roles. That is where the enteredRegion and exitedRegion events the behaviour layer reacts to come from.

05

Extending without touching the core

The last part is not a class but an agreement. Wherever properties appears, a programme may store its own keys: a voting application puts voteWeight there, a board game healthPoints, a museum installation language, a planning tool taskId. The core does not move with it.
